# Architecture decisions

## 001 – Station IDs instead of station names
**Context:** Using station names instead of station IDs does not lead to errors with the API, but a name cannot be uniquely matched to one station. This can lead to ambiguity in the connections search, where a most likely station is being chosen instead of the one the user wanted. The biggest problem is that this happens without any warning so the user does not know which station effectively got chosen.
**Decision:** Stations are saved by ID and not by their name, the ID comes from the official station number. We use the ID when searching for connections and we use the name of the station when the user types in which connection they want to check.
**Alternatives:** Alternatively we could just save the name and each time we need it, we need to send an API request with the name to the /locations endpoint so that we know its unique ID. With this we need to send unnecessary API requests each time, this slows the whole process down. Further the API might change and so the order of the stations. With saved routes this causes silent problems, where a user thinks they calculated a route from A to B but in the meantime B is not B anymore but C because the API changed silently. Only because maybe Pfäffikon ZH (C) is now ranked higher by the API than Pfäffikon SZ (B).
If we decide to use our own ID, we would need to create some sort of function that translates names to IDs and then again to the IDs that can be used with the API.
**Consequences:** Using the station ID, we not only reuse something that already exists, which leads to less management on our side, but we also get uniqueness and solve our ambiguity problem. Further when the user decides to save a route, we need to save id and name of the stations. We get this information from the station the user decided on after we send them the list of possible stations from our locations request. From the location request we then get ID and name of a station for start and destination. So we always need a search and selection step from the user, before we can go and calculate a connection.

## 002 – `JsonPropertyName` Attribute to deserialize API responses into DTOs
**Context:** In the API that we use we get properties in camelCase and in C# we have properties in PascalCase. When deserializing the JSON of the API response we need to consider this or otherwise our DTO properties might just silently not be filled.
**Decision:** We decided to use the `JsonPropertyName` attribute so that the programmer needs to exactly define the name of the property of the API response
**Alternatives:** One alternative would be the `JsonSerializerDefaults.Web` setting, this would globally activate the conversion of camelCase into PascalCase instead of per property. The `JsonPropertyName` gives us finer granularity. Otherwise we could of course just use camelCase for the property names in C#, but we do not do this, since the standard naming conventions of C# already have camelCase reserved for variables, with this no one could tell if something is a variable or a property just by reading the code. 
**Consequences:** C# properties can easily be renamed, this does not affect the JSON property. Everything is more readable and someone who reads the code knows immediately which response property belongs to which property in C#. On the other hand the code is filled with the attributes `JsonPropertyName` and every time a new property is added, the attribute must be written too. Also if there is a typo in the `JsonPropertyName` the serializer would just silently ignore it and not fill the property. This risk will be mitigated by tests against a recorded real API response.

## 003 – Testing the HTTP client with a stub `HttpMessageHandler` and recorded responses
**Context:** We do not want to send real requests over the network for each test. This is because network requests might take very long to send, this can be a problem if we execute the tests often. An HTTP client usually sends requests over the network. This might lead to errors on the server side of the API and it can make the tests fail unexpectedly. When validating an API that sends responses that constantly change, for example the delay for a connection, sometimes our tests will fail and sometimes not, the test data is not static but dynamic. `HttpClient` delegates every request to an exchangeable `HttpMessageHandler`, which allows us to replace the network with a fake.
**Decision:** We decided to use a stub `HttpMessageHandler` class and recorded responses in JSON format to test the HTTP client. Further we save the last request in the http message handler stub class so that we can also check if the request was correct. The recorded responses are the raw JSON body that is returned from the actual API.
**Alternatives:** We could make real API calls. This might introduce API errors that we must handle, it might introduce delays and dynamic test data. Moq would be a bit difficult to implement, since we have to override the `SendAsync` method of the HTTP message handler but this method is protected. Third party libraries would work, but they again add dependencies that need to be maintained. Using handwritten responses is a possibility, but creating accurate and valid API responses by hand is more tedious and error-prone than just sending a request once. On the other hand, handwritten responses are useful for cases that are hard to record, for example a delayed train.
**Consequences:** We can test and make up responses. The tests run fast and are deterministic. Error codes like an error code 500 can easily be tested. We do not need to rely on a real network. With this our tests are stable, but do not recognize API changes. There could be a contract test that runs nightly and checks if the saved responses used in testing can be recreated with the current version of the API and if that is not the case we have to update the responses and our tests.

## 004 – Custom `JsonConverter` for the transport API timestamps
**Context:** We get a datetimeoffset from the API that is not ISO-conform (it sends +0100 instead of +01:00 for the offset which is expected of `System.Text.Json`), this causes the JSON deserializer to fail upon deserializing the JSON from the API into a DateTimeOffset property. We detected this by running a test against a recorded response that threw a JsonException at `$.connections[0].from.departure`.
**Decision:** We decided to make a new class and derive it from `JsonConverter<DateTimeOffset>`. In this class we replace the parsing of the datetimeoffset with a `DateTimeOffset.TryParse` using `CultureInfo.InvariantCulture`. The custom converter is then applied via attribute, since we want to have more granular control over which property uses which converter. Upon receiving invalid values, the custom converter throws `JsonException`.
**Alternatives:** Alternatively we could create an additional string property in the DTO, that gets the raw JSON datetimeoffset and we could adjust the setter of this string property so that it automatically converts to ISO-conform datetimeoffset and sets it into the DateTimeOffset property. The downside is that we have to use this approach for every datetimeoffset we want to use from the API. Another approach could be to use the departureTimestamp value of the API instead, with the destination this works and we can just switch to using timestamp, the problem is prognosis, another object, of the JSON response we want to use, does not have a timestamp so we can't calculate when the train will be late since we can't parse the prognosis. Further there is an alternative approach on how to apply the `JsonConverter<DateTimeOffset>`, that is by passing a `JsonSerializerOptions` object to the methods that use the converter. With this we do not need to set the attribute on every property, but we do not have granular control over which property uses which converter. A benefit of this converter approach is, that the DTOs remain clean, we do not have a huge amount of attributes that we might forget to add on future properties of the same type and we only have to set the converter at one place.
**Consequences:** We use `DateTimeOffset.TryParse` in the custom converter, this is much more tolerant than the standard JSON serializer. A timestamp without an offset (e.g. `2026-11-09T07:19:00`) would be accepted silently by `DateTimeOffset.TryParse` and the server's local offset would be assumed (could be UTC time). We might forget to set the JSON converter attribute on future properties, the good thing is a test of the recorded connections response will catch this error and fail. 

## 005 – Configuration via the Options pattern with validation at startup
**Context:** The transport API must be configurable. Configurable options are `BaseUrl` and `TimeoutSeconds`, these must be set. Configuration options if not validated can cause different kinds of errors ranging from `NullReferenceException` to `InvalidOperationException`. For example if configuration options are set to null or not set at all or they are invalid (string in an int option). The worst thing that can happen are errors in production, if by any chance the `TimeoutSeconds` configuration option is left out it is silently set to 0, this would cause an immediate timeout every time someone tries to send a request.
**Decision:** We decided on using the options class `TransportApiOptions` with a section name, this way we bundled all the configuration options in one place and could validate them with DataAnnotations like `[Required]`, `[Url]` or `[Range(1, 120)]`. Further we needed to add a custom rule to the validation, so that we could check that the `BaseUrl` configuration option is actually a base URL ending with a slash (without a slash at the end the base URLs would not be correctly connected to the relative URL, the last path segment `v1` would be replaced when the relative URL is resolved (RFC 3986)). We decided on adding an additional null check in this slash validation, since one of our tests that used null for the `BaseUrl` configuration option failed with a `NullReferenceException` instead of an expected `OptionsValidationException`. To avoid any errors in the configuration we decided to use `ValidateOnStart()` so that errors are caught right away at the start of our application, this causes the application to fail as fast as possible to not drag errors into production. We also decided to not use an actual URL as default value for the `BaseUrl` configuration option, so that missing configurations would lead to an error in the validation instead of silently using default values (we decided on using `string.Empty`). The whole validation and the registration of the `TransportApiClient` is implemented inside the extension method `AddInfrastructure()`, this way `Program.cs` can just call this extension method without needing to know any details. 
**Alternatives:** 
- **Reading values directly** via `configuration["TransportApi:BaseUrl"]`: With this we would need to implement type conversion for each property since the direct access always returns `string?`. Further we also have to develop the whole validation. With time it would be scattered across the code, instead of happening once at startup. Errors while reading configuration options, occur during production if we use this approach, instead of getting all the errors on startup before the app even opens. If we have a typo in the string that defines which configuration option we want to read, we have to manually correct it on every occasion. Most importantly if we directly try to read the configuration options, they can be missing, but would still silently work and just give us null as value, this would lead to errors later on that are rather hard to trace back. 
- **Options pattern without `ValidateOnStart()`:**  We would have one place where the whole validation happens and we would still be using the Options pattern. The problem with this is, that only during production we see certain errors, because here with this approach we would access the configuration during the first request not before that. We want our app to fail fast and tell us immediately if and what error occurred. With this approach the customer is the first to realize the mistake in the software, in our case when no delay notification is sent because of a configuration error. 
- **Default values in code:** `BaseUrl = "https://transport.opendata.ch/v1/"` and `TimeoutSeconds = 30` as defaults. This can be quite nice to use, this way even if we forget to set a configuration option for the two properties, we have fallback values. This can come in handy, but also brings a great risk with it. If we forget to change URL or have not set the values at all, we do not see any errors, instead everything seems to work. Again only the customer will notice errors and no one could really tell that they are coming from a bad config. Let's say someone wants to test a new function against a test system that is hosted on another `BaseUrl`, let's assume the developer accidentally forgets to change the config or has a typo in their config, we would silently fall back to the default production system and execute possibly faulty code there.
- **Registration directly in `Program.cs`:** With this we would have to duplicate the registration, meaning we have to copy options and validation and maintain it at multiple different places. If something is forgotten in one registration, the API and the Azure Function would work differently for different registrations. With one `AddInfrastructure()` method that everyone has to use for registration, we have one centralized place where the registration is done. Testability is also a factor, without `AddInfrastructure()` we need to start the app each time we want to test different registrations, with the method we do not have to do this. With `AddInfrastructure()` we have also encapsulated infrastructure in such a way that `Program.cs` does not need to know how the `TransportApiClient` is configured. 
**Consequences:** 
- **Benefits:** Through the decision of using our own options class `TransportApiOptions` we get several advantages: fail fast right at the start of the app not at the first request, we parse the config into clearly defined properties with a type, we do not have magic strings that hide any context. With `AddInfrastructure()` we have one centralized place, that all the registrations go through. With validation through annotations we also used a custom null check for the `BaseUrl` since its type is string but that is a reference type, meaning it should not be null but could be if an internal mechanism sets it via reflection. Therefore we added a null check in `AddInfrastructure()`. For the `TimeoutSeconds` that is of type int, it is a value type meaning no null can be held by this property. Further through the `[Range(1, 120)]` annotation the property is directly protected from invalid values outside of the valid range. 
- **Limitations and surprises:** We also noticed that when entering values like "1.5" or "" the binding of the property fails directly with `InvalidOperationException`, since the values can not be converted to `int`. This surprised us, since all the other tests would throw an `OptionsValidationException`. Further with the use of `ValidateOnStart()` comes the downside, that we can not use this in the tests. To validate the config options there, we simply try to access the `.Value` of `IOptions<TransportApiOptions>`, which starts the validation so we get the same behavior as when starting the app. 
- **Safeguards:** The whole registration is tested with multiple tests that expect certain exceptions and certain error messages, also we made a mutation test which uses `GetRequiredService<TransportApiOptions>` without `IOptions` so that when running the test fails, that normally should prove that the code is working. When accessing the temporarily manipulated code the test failed, without the manipulation it was green so we knew that if someone mistakenly didn't use `IOptions<TransportApiOptions>` the test would have caught it.

## 006 – Skip invalid entries from the transport API and log a warning
**Context:** The API might send responses where required information is missing e.g. departure in from.
**Decision:** We decided to skip and log entries where required information is missing. The `TransportApiClient` logs the requested data that leads to these entries. The `TransportApiMapper` returns null for such entries that are missing required information. 
**Alternatives:** 
- We could throw an exception, that would lead to a clear information. Problem with this is that we do not get the rest of the correct connections. 
- We could use default values, that would have the consequence that we do not show the actual data of the API and show the user something that is not the truth. 
- We could just silently ignore these entries and not log them, but nobody would notice that the API delivers broken data.
**Consequences:** The API might respond with only invalid entries, this would be shown to the user as an empty list of connections or "no connection could be found". The difference between only invalid entries and no connections could be found can only be seen in the log. Still the user will get all valid connections, if only a part of the connections in the response of the API are invalid. We secured the functionality of the mapper to detect missing required information by testing the mapper against any missing required field and we also made a client test with an invalid entry between two valid connection entries.
