# Architecture decisions

## 001 – Station IDs instead of station names
**Context:** Using station names instead of station IDs does not lead to errors with the API, but a name cannot be uniquely matched to one station. This can lead to ambiguity in the connections search, where a most likely station is being chosen instead of the one the user wanted. The biggest problem is that this happens without any warning so the user does not know which station effectively got chosen.
**Decision:** Stations are saved by ID and not by their name, the ID comes from the official station number. We use the ID when searching for connections and we use the name of the station when the user types in which connection they want to check.
**Alternatives:** Alternatively we could just save the name and each time we need it, we need to send an API request with the name to the /locations endpoint so that we know its unique ID. With this we need to send unnecessary API requests each time, this slows the whole process down. Further the API might change and so the order of the stations. With saved routes this causes silent problems, where a user thinks they calculated a route from A to B but in the meantime B is not B anymore but C because the API changed silently. Only because maybe Pfäffikon ZH (C) is now ranked higher by the API than Pfäffikon SZ (B).
If we decide to use our own ID, we would need to create some sort of function that translates names to IDs and then again to the IDs that can be used with the API.
**Consequences:** Using the station ID, we not only reuse something that already exists, which leads to less management on our side, but we also get uniqueness and solve our ambiguity problem. Further when the user decides to save a route, we need to save id and name of the stations. We get this information from the station the user decided on after we send them the list of possible stations from our locations request. From the location request we then get ID and name of a station for start and destination. So we always need a search and selection step from the user, before we can go and calculate a connection.

## 002 – `JsonPropertyName` Attribute to deserialize API responses into DTOs
**Context:** In the API that we use we get properties in camelCase and in C# we have properties in PascalCase. When deserializing the JSON of the API response we need to consider this or otherwise our DTO properties might just silently not be filled.
**Decision:** We decided to use the `JsonPropertyName` attribute so that the programmer needs to exactly define the name of the property of the API response
**Alternatives:** One alternative would be the `JsonSerializerDefaults.Web` setting, this would globally activate the conversion of camelCase into PascalCase instead of per property. The `JsonPropertyName` gives us finer granularity. Otherwise we could of course just use camelCase for the property names in C#, but we do not do this, since the standard naming conventions of C# already have camelCase reserved for variables, with this no one could tell if something is a variable or a property just by reading the code. 
**Consequences:** C# properties can easily be renamed, this does not affect the JSON property. Everything is more readable and someone who reads the code knows immediately which response property belongs to which property in C#. On the other hand the code is filled with the attributes `JsonPropertyName` and every time a new property is added, the attribute must be written too. Also if there is a typo in the `JsonPropertyName` the serializer would just silently ignore it and not fill the property. This risk will be mitigated by tests against a recorded real API response.

## 003 – Testing the HTTP client with a stub `HttpMessageHandler` and recorded responses
**Context:** We do not want to send real requests over the network for each test. This is because network requests might take very long to send, this can be a problem if we execute the tests often. An HTTP client usually sends requests over the network. This might lead to errors on the server side of the API and it can make the tests fail unexpectedly. When validating an API that sends responses that constantly change, for example the delay for a connection, sometimes our tests will fail and sometimes not, the test data is not static but dynamic. `HttpClient` delegates every request to an exchangeable `HttpMessageHandler`, which allows us to replace the network with a fake.
**Decision:** We decided to use a stub `HttpMessageHandler` class and recorded responses in JSON format to test the HTTP client. Further we save the last request in the http message handler stub class so that we can also check if the request was correct. The recorded responses are the raw JSON body that is returned from the actual API.
**Alternatives:** We could make real API calls. This might introduce API errors that we must handle, it might introduce delays and dynamic test data. Moq would be a bit difficult to implement, since we have to override the `SendAsync` method of the HTTP message handler but this method is protected. Third party libraries would work, but they again add dependencies that need to be maintained. Using handwritten responses is a possibility, but creating accurate and valid API responses by hand is more tedious and error-prone than just sending a request once. On the other hand, handwritten responses are useful for cases that are hard to record, for example a delayed train.
**Consequences:** We can test and make up responses. The tests run fast and are deterministic. Error codes like an error code 500 can easily be tested. We do not need to rely on a real network. With this our tests are stable, but do not recognize API changes. There could be a contract test that runs nightly and checks if the saved responses used in testing can be recreated with the current version of the API and if that is not the case we have to update the responses and our tests.
